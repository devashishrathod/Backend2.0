Every button, where it sends the reader, and who owns that page

58 buttons across 42 templates  ·  Prepared 08 Sep 2026

What this is for

Each WhatsApp message carries one or two buttons. This lists every one of them: the URL that is registered with Meta, the constant in the backend that builds it, what the dynamic part of the URL contains, and the front-end route that has to exist for the tap to land somewhere.

The rule behind every destination: a button opens the exact record the message is about, never a list. A payment notification opens that payment; a refund notification opens that refund. The only exceptions are the plan list — where the vendor is choosing, so a list is the point — and the onboarding and dashboard screens, which are single pages.

⚠️ A URL is frozen when Meta approves the template

Everything below has to be right before a template is created, not after. If a route changes later, the template has to be built again under a new name and the old one keeps sending in the meantime. So a "NEW" or "Confirm" row in the last column is a blocker, not a to-do.

Sign-in behaviour

SurfaceWhat happens when the reader is not signed in
Vendor panel
https://vendor.trydood.com		The panel's own auth guard shows the login screen, then continues to the requested page. Nothing is appended to the URL — the route is the destination.
Admin panel
https://admin.trydood.com		Same as the vendor panel.
Customer app
https://app.trydood.com		App installed and signed in: opens that screen. Signed out: login, then that screen. Not installed: the link opens in a browser, and whatever is served at that host decides — it should send the visitor to the store. That decision cannot be expressed in the link, so it belongs to the page at that host.
Document download
https://api.trydood.com		No sign-in. The token in the URL is the authorisation, which is why it is long and unguessable.
Website
https://trydood.com		Public page, no sign-in.
